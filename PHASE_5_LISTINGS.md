**Status: complete and validated end-to-end against the local Supabase stack**, including real Storage uploads to the `listing-images` bucket, a real admin MFA (TOTP) session driving the moderation flow, and every status transition — plus two separate self-escalation attack attempts — exercised through the actual HTTP API. This phase closes the listings-table half of `AUDIT_REPORT.md` RLS-02 (already resolved by Phase 2's construction — verified, not re-fixed) and FE-01 (client-side duration parsing), and finds and fixes two new, real authorization/visibility bugs that no code review would have caught.

## How this was verified

Typecheck (`npx tsc --noEmit`) and lint clean throughout. Then full runtime testing against the local Supabase stack (`supabase db reset` + real HTTP calls), specifically probing the two things a code review can't catch: whether an authorization gap is actually exploitable, and whether a cross-table RLS dependency actually resolves for the role that will really call it.

1. **Self-escalation attempts, as the agency owner (not admin):**
   - `INSERT ... status: 'published'` directly on creation → `403 INSUFFICIENT_PRIVILEGE: cannot create a listing with status published`.
   - `INSERT ... featured: true` directly on creation → succeeds (200), but the row comes back with `featured: false` — silently re-pinned, not rejected (matches the `lock_message_content` precedent).
   - `UPDATE ... status: 'approved'` directly from `draft` → `400 INVALID_TRANSITION` (graph check).
   - `UPDATE ... status: 'approved'` from `pending_review` (a structurally valid graph edge) → `403 INSUFFICIENT_PRIVILEGE: only an admin may set listing status to approved` (the second, role-based check).
   - Confirms the trigger's two layers (data-integrity graph vs. admin-only authorization) both actually hold, not just one of them.
2. **Legitimate lifecycle, end-to-end:** draft creation → submit for review → **admin approves with a real AAL2 TOTP session** (same enrollment/challenge/verify flow proven in Phase 3/4, reused rather than re-derived) → agency publishes the now-approved listing. Each step verified by reading back the actual row, not just checking for a 200.
3. **Storage**, both buckets exercised this phase touches:
   - Legitimate image upload to `listing-images/<agency_id>/<listing_id>/...` by the owning agency → `200`, followed by a successful `listing_images` metadata insert.
   - Illegitimate upload to the same path by an unrelated authenticated user (not agency staff) → `403`, cleanly rejected by `has_agency_access()` (the same function fixed for recursion in Phase 4 — this test also re-confirms that fix generalizes correctly to a second, independent bucket).
4. **The `agencies_public_select_approved` bug** (found, not assumed): testing the public agency-profile query as `anon` returned an empty result for an agency confirmed, via direct SQL, to be genuinely `approved`. Diagnosed by checking `agency_verification` visibility directly as `anon` (`SELECT ... — 0 rows`), which showed the real cause: `agency_verification` has no anon-visible SELECT policy at all (deliberately — it holds rejection reasons and review notes), so the `EXISTS(SELECT ... FROM agency_verification ...)` subquery inside `agencies_public_select_approved`'s own USING clause silently sees zero rows for `anon`, regardless of the agency's real status — the same cross-table-RLS-dependency bug class as Phase 4's `has_agency_access()`/`conversation_participants` recursion, but manifesting as a silent empty result instead of an error. Fixed with the same pattern (a `SECURITY DEFINER` helper, `is_agency_publicly_approved()`), then **re-tested twice**: an approved agency is now visible to `anon`, and a separately-created `draft`-status agency is correctly still invisible. A second, related instance was then found in my own newly-written frontend queries (`usePublicAgencies`, `AgencyProfile.tsx`, `ActivityDetail.tsx` all originally embedded `agency_verification!inner(status)` in the same request) — the embedded join has its *own* RLS check, independent of the now-fixed `agencies` row policy, so it hit the identical wall. Fixed by removing the redundant embed entirely (the `agencies` row policy already guarantees only approved rows are visible), re-tested clean.

## What Phase 5 deliberately did not do

- **Did not build any departures/inventory/blackout-date/seasonal-pricing UI.** Migration 4's own Phase 2 comments assign the pricing-resolution engine to Phase 8 ("this migration only creates the tables so Phase 8 has somewhere to build") and `PHASE_0_FORENSIC_AUDIT.md` assigns the availability/inventory engine to Phase 7. `AgencyAvailability.tsx`, `BulkRangeDialog.tsx`, `SeasonalPricingDialog.tsx` still target the old flat `availability` table and remain broken against the current schema — not worsened by this phase, but not fixed either. **A published listing currently has no usable departures or bookable capacity** — it exists in the catalog and is browsable, but end-to-end booking is not yet possible, which is expected at this point in the phase sequence.
- **Did not add per-image moderation.** `listing_images` has no `status`/`approved` column — an agency's uploaded photos go live the moment the whole listing is approved, with no individual image review. Relies entirely on listing-level moderation to catch inappropriate content.
- **Did not add an agency logo.** `agencies` has no `logo_url` column; `AgencyProfile.tsx` always shows the initials fallback. Not built because it wasn't blocking anything in this phase's scope and would have meant inventing a new bucket/upload flow not called for by any existing requirement.
- **Did not send an email to the agency on listing approve/reject.** Phase 3's own `record-audit-log` code comment explicitly scopes Listings moderation to the generic audit-log pattern (unlike Phase 4's agency-verification flow, which does email); kept consistent with that stated design rather than inventing new scope.
- **Did not fix `useMessages.ts`'s remaining old-schema lookup** (`.from(...).select(...).in("user_id", agencyIds)`, presumably targeting the gone `agency_applications` table) — found while checking `AgencyProfile.tsx`'s "Message Agency" button, but that broken code path is in a *different* function (`useConversations`, for listing/displaying existing conversations) than the one `AgencyProfile.tsx` actually calls (`useStartConversation`, whose `mutationFn` only ever writes `agency_id` — already correct, no `user_id` lookup involved). Confirmed not a blocker for this phase's own testing; left for messaging's own phase (Phase 16 per earlier audit references) rather than partially fixing an unrelated file.

## Risks / things to verify before Phase 6

- **The cross-table-RLS-dependency bug class now has two confirmed, independently-discovered instances** (Phase 4's `has_agency_access()`/`conversation_participants` infinite recursion, and this phase's `agencies_public_select_approved`/`agency_verification` silent-empty-result). Both were found only by testing as the *specific role* the feature is meant to serve (an unprivileged attacker; an anonymous visitor), not as an authenticated staff/admin account. **Every future phase that adds a public-facing (anon-reachable) RLS policy with a cross-table `EXISTS`/embedded-join must be tested as `anon` specifically**, not assumed correct because the SQL "looks right" or because it works when tested as a logged-in user.
- **`category`/`difficulty` are now hard-coded check constraints matching the exact strings already used across ~8 frontend files.** Adding a new category in the future is a coordinated schema-migration + frontend change, not a config toggle — this is a deliberate trade-off (see the reasoning in migration 4's own comment), not an oversight, but worth remembering before anyone reaches for "just add a category" as a quick change.
- **No automated regression test covers either of this phase's two guard triggers or `is_agency_publicly_approved()`.** All verification was manual, direct HTTP/SQL, this session — a future "simplification" of any of these three functions could silently reintroduce either bug class with nothing catching it until a real request fails (or, worse, silently returns wrong-but-plausible-looking empty results, as the agency-visibility bug did).
- **A listing can be `published` with zero departures/inventory.** Nothing in this phase's UI or database prevents that, since departures/inventory are explicitly out of scope here — Phase 7 needs to decide whether "published but unbookable" is an acceptable transient state or whether publishing should eventually require at least one active departure.
